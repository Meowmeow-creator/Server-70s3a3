## 1. 现象

- 玩家（roleId=8，冰结师「12345」，Lv70）在副本里走到**稀有度 2（紫色）** 材料上按拾取键（X）：
  - **角色做出弯腰拾取动作**；
  - **客户端不发出任何拾取请求**（服务端日志零 `FRAME opcode=46`）；
  - 物品不进包；
  - 本局之后所有手动拾取全部失效，直到重登客户端。
- **白色（rarity 0）/ 蓝色（rarity 1）物品完全正常**。
- 与物品来源无关：怪物掉落、自己丢弃到地上（op40）都同样卡。

## 2. 已确认的事实（含证据）

### 2.1 服务端无责任
- 到达服务端的请求全部正确处理：白色碎布片 3030、蓝紫玛瑙 3019、炉岩炭 3171、金币均 `PICKUP_COMMITTED` 正常。
- 稀有物品卡住时日志里**根本没有 op46 帧**（客户端本地拒绝，服务端不知道玩家按了键）。
- 拾取应答包（op39）在 4 个历史构建中反射调用**逐字节一致**（FG375 10-28 22:08 / FG381 01:34 / 02:35 / 当前），`PickupGroundFG201`/`Pickup`/`CollectionChanged` 方法 IL 长度零变化，wire 层代码 10-28 22:06 后未改。**不是服务端回归**。
- 10-28 能连捡 6 件是因为那批掉落全是白色装备/金币 + 蓝炉岩炭（见 2.2）。

### 2.2 唯一分界 = 物品 rarity
| 结果 | 物品 | rarity |
|---|---|---|
| 能捡 | 3019 紫玛瑙 / 3171 炉岩炭 / 3030 碎布片 / 金币 / 18408、37305、27001（白装） | ≤1 |
| 卡死 | **3221 灾难的征兆 / 3187 灵魂晶石 / 3249 卡勒特干部的徽章 / 2749124 镶嵌栏开启装置** | **2** |

- PVF 全字段 diff（3019 vs 3221）：grade/weight/icon/type/group/price/move wav 均有差异，但**只有 rarity 在全部正反样本上一致**（2749124 是 `[etc]` 不是 material，同样卡死 ⇒ 与物品类型无关）。
- 对照实验（玩家实测）：同房间里先捡白色 → 成功；再去捡紫色 → 卡。把紫色物品**丢到地上再捡** → 同样卡（排除「怪物掉落数据」问题）；系统设置里**没有**「拾取确认」类选项（排除设置）。

### 2.3 客户端侧行为（内存实测）
- 定位本地角色对象：全局 `0x18AFF18` → `+0x3C` 缓存 actor 指针；查表函数 `0x36DFA0(uid)`、getter `0x36E1C0`；actor 已知字段 `+0x2B8` 心情精灵、`+0x2C8` 情绪。
- 80ms 轮询 actor（`local-run/ida-work/actor_watch.py`）抓两次按键：
  - **白色成功**：动作阶段 `+0x0034` 推进 `0→1→2`，随后 **背包区域 `+0x1A54` 起约 300 字段更新**（物品进包）。
  - **紫色卡死**：动作阶段 `+0x0034` 从 `2→0` **回滚**，**背包区域零更新**。
  - 结论：客户端**启动了拾取动作又在「发请求」前撤销**，不是死锁；每次按键独立判定。
- 改内存里的物品定义（3 处候选）全部无效：**物品名字颜色仍是紫色** ⇒ 那几份都是**缓存副本**，显示和判定都不读它们。

## 3. 已排除的定位路径（不要重复）

| 路径 | 结论 |
|---|---|
| 静态收发分发表 `0x390C04` | **死表**（FG366b 曾挂钩子逐字节核验，0 命中）；真 handler 运行时构建 |
| 运行时表 `{hash, 0x8800+偏移, handler, 0}` | 全内存扫描未命中；已知真 handler（op217=0x47E830）在内存**零引用** |
| 客户端「写 opcode 0x2E」 | `mov byte[reg],0x2e` 唯一命中是 `push 0x12e01c6` 立即数的误报 |
| 键位系统 xref（0x18C18F0 / 0x18B045C / 0x9CF170） | 全是设置 UI；游戏内按键不走这些全局 |
| 高频被引用函数 | 全是 CRT / 字符串解密 `0x10B0C20` / secure-CRT 漏斗 `0x128E513`；**无统一发包函数**（发包走虚函数） |
| 27 字节步长扫描 | `0x118xxx` 区域是别的 27 项表（memcmp/资源），非掉落行解析 |
| `cmp …,2/3` 稀有度阈值对（991 对） | 反编译审查后全是字符串比较/结算/UI |
| `mov [reg+0x34],0` 状态清零（23 处） | 反编译后全是构造/析构/UI 状态机，与拾取无关 |
| 3221 内存命中（533 处） | 全是图标/资源引用；无「itemId+rarity」定义结构 |
| PVF 标签字符串 `[rarity]`/`[grade]` | 找到标签池（`0x10afd464` 等）但无代码引用可追 |
| 插件节 `.qp81/.qp82` | 是之前会话打的 op358/407 拦截桩，与拾取无关 |
| op38 死亡包处理器区域 `0x780750` | **控制流混淆**代码（大量 push/pop/xchg/lea esp），静态不可读 |

**关键地址**：
- 本地 actor：`[0x18AFF18]+0x3C`；`actor+0x2C8`=情绪；`+0x2B8`=心情精灵
- 物品定义**副本**（死数据）：`0x63783cc0` 附近，0x30 步长，itemId@+0、rarity@+5（改动无效，勿再试）
- 名字池：GBK「灾难的征兆」`0x1122a0a4`；UTF-16 多份
- PVF 文件表：`0x11a3cc08` 附近，`[路径 0x20][4B][文件 id]`，`material/sign_calamity.stk` 的文件 id = `0x88036000`
- 拾取请求：op46，16 字节净载荷（slot@0、坐标@4/6/10/12），cipher index = 46%14 = 4

**服务端 GM**（用于投放物品做对照）：请求文件 `<store>\TestTools\<32hex>.gm.xml`，token 在 `TestTools\service.xml`；`op="item"` 要求角色在城镇，`op="loot-pickall"` 副本内可用。GM 拾取能把紫色物品放进背包（已实测）。

**日志判别法**：`FRAME opcode=46 bytes=29` 有无 = 客户端是否发出请求；`PICKUP_COMMITTED` = 服务端是否入库。注意 `opcode=464` 会误匹配，必须带 `bytes=29`。
