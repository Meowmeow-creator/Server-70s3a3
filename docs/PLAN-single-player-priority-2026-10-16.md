## 1. 排序原则（单机玩家视角）

1. **先修"每天都会撞"的系统**：任务主干、掉落、强化、副本机制 —— 玩家 100% 时间在这些系统里。
2. **再补"缺内容"**：区域任务链、塔、副本 —— 决定能玩多久（长线）。
3. **后修"手感与文案"**：AI、迷宫随机、对话 —— 影响沉浸但不动玩法骨架。
4. **明确排除**：PVP/比武场、拍卖行、个人商店与交易、公会/社区/好友、多服基建（Relay/Manager/UDP/反作弊）
   —— **单机语义下无意义**，不做。
5. 同一批次内：**先做不需要新协议、不需要原版文件的**（可离线自证），把"需真人抓包/需原版数据/需产品决策"的单独列清单。

## 5. 转职系统审计（2026-10-17，按用户要求）

**已实现且已接线（证据为代码路径）**：
1. 任务完成时若 `RewardGrowType>0`（来自 PVF `[grow type] N`），`Batch-Service-FG.cs:143` 走
   `Offline70JobAdvancementFG91.Reply(...)` 发 **op36 成长回包**（grow 字节 + 技能库），而不是普通奖励回包；
   同时发 `job-skills`（`SkillsReplyFG129`）、`Appearance()`、`job-attributes`，并记 `JOB_PROMOTED grow=N`。
2. 成长值写入同一个经济事务：`Progression-FG.cs:86` 设 `s.GrowType`，`DeliverQuestAwards` 里再核对
   `GrowTypeCredit`（冲突则拒绝），所以"转职"是原子且可重放的。
3. 客观侧：`[job change quest]` 段落 → 记录的 `JobChange=true`；生成器守卫 `grow>1` 拒收（引擎只支持首次）。

**缺口（按单机可见度排序）**：
1. **角色职业字段从不改变**：`s.Job` 全仓没有任何写入点（`grep "\.Job="` 只命中物品定义与探针）。
   转职后只变 `GrowType`，`Job` 仍是 0 ⇒ 客户端可能仍按"未转职职业"渲染，带职业限制的物品/技能判定也不会随之变化。
   **需要真人一局验证**：转职后客户端的职业名/技能栏/可穿装备是否变化。若不变，就要在事务里同时写 `Job`（并解锁引擎的
   `s.Job!=0` 前置，从而支持二转）。
2. **不给新职业技能**：op36 里发的技能库是角色**当前**技能（`Offline70SkillSlots`），不是目标职业的技能表；
   新职业的技能要么由客户端自行授予，要么需要服务端按职业表发放（PVF 有技能表，但需要证据确认原始行为）。
3. **二转/觉醒（grow 2..4）被引擎前置挡住**：`s.Job==0 && s.GrowType==0` 只允许首次。放开需要第 1 条先成立。
4. **`[awakening type]` 奖励（38 条）没有对应机制**：它是"觉醒层数"，与 grow 的关系（是否同一字节）未求证。

**结论**：转职链在"任务 → 成长回包 → 客户端刷新"这一段是完整的；**不完整的是角色状态本身（Job）与后续层级（二转/觉醒）**。
下一步：先用真人在游戏里做一次转职（或我造一个隔离角色走一遍）确认客户端表现，再决定是否同时写 `Job` + 放开二转。
