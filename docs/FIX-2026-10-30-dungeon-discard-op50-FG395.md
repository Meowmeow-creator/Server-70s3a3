# FIX 2026-10-30：副本内丢弃被服务端整体拒绝（FG395，op50 确认标志位）

状态：**已编译部署，双服 04:49 重启**（`rareAutoPickup=1`）。待实机验收。

## 1. 现象（用户 2026-10-30 报告）

- 副本内不能丢弃装备、也不能丢弃紫色材料，**没有任何提示窗口**；
- 紫色道具一掉出来就自动进包（即 FG392 的 `rare-auto-pick.on` 服务端代收在起作用，见 §4）。

## 2. 根因：op50 丢弃请求从来没被服务端接受过

日志（channel-evidence.log 04:36:28 / 04:37:46）里有用户真实发出的两条 op50 丢弃请求，
全部被服务端拒绝：

```
REJECTED opcode=50 reason=Drop50 reserved or padding
```

解密两条实机请求（`channel-evidence.log.request-50-16/71-*.bin`，flow cipher index 8）得到真实布局：

```
{X u16, Y u16, list u8, slot u16, 数量 u32, 确认标志 u8 = 1, 4 字节 0}
```

- 04:36 那条：X=309, Y=293, slot=25（**装备页**）——用户丢装备；
- 04:37 那条：X=480, Y=418, slot=136（材料页末格）——用户丢紫色材料。

旧解析器要求 11..15 字节全 0，而客户端把第 11 字节当**确认标志置 1**（和 op18 城镇删除的
confirm 位同族，FG367 当时也踩过同一类坑）。所以**副本内丢弃自上线以来一次都没成功过**；
10-29 调查文档里"自己丢弃到地上"的对照实验实际走的是别的路径。

## 3. 修复（FG395）

| 文件 | 内容 |
|---|---|
| `Item-Drop-Protocol-FG.cs` | `Parse`：第 11 字节接受 0/1（确认标志），只校验 12..15 为 0；其余边界检查不变 |
| `Batch-Service-FG.cs` | `Discard`：**时装(Kind3)/装备(Kind4) 的副本内丢弃改为直接销毁**（原子事务、收据防重、`DROP_DELETED` 日志 + op50 回包 + op14 背包增量），不再走"Only verified consumable…"拒绝；消耗品/材料/徽章/副职材料(Kind 1/2/9/10) 维持原地面生成路径（op40 通知 + op14） |

装备不走地面生成的理由：36 字节的地面行（Native49C920 形状）从未被客户端验证过，而原版
`WarRoom::HandleItemDrop` 对多数装备本来就拒发（itemType<10 / 0xb → 0x17）；单机场景"丢掉=销毁"
语义等价（原版掉落物离开房间也会消失），还避免了装备落地后捡回丢失强化/耐久的问题。

## 8. 跟进（04:55）：落地行布局按原版重写

04:50/04:51 两条实机丢弃**服务端全部成功**（`DROP_COMMITTED slot=132 ground=2005/2006 item=3303`），
但玩家看到"丢不下去"——op50 回包形状与原版一致（✓），**op40 落地行不是**。原版
`CParty::drop_item`（rednf drop_item.inc，ORIG 0x85a71xx）成功尾部是：

```
op40: uid(u16), X(u16), Y(u16), 地面槽(u16), itemId(u32), attr(u8), 数量(u32),
      耐久(u16), fieldd(u32), 放大类型(u8), 放大值(u16), put_packet(Inven_Item)=4 字节 0, 1(u8)
```

共 **31 字节**；旧的 36 字节猜测形客户端解析不出 → 地面不生成物品。已按原版重写

同时从原版拿到的两个语义锚点：

1. **原版禁止丢弃品级>2 的物品**（`get_rarity()>2 → 0xd` 稀有度限制）——装备/时装销毁路径
   与原版"多数装备禁抛"一致，品级 2 的紫色材料可以丢（用户的 3303 正是品级 2）；
2. op50 回包 `{1, type, slot u16, count u32}` 与我们现有实现相同，无需改。

用户 04:50/04:51 丢掉的 2 个英雄的宿命(3303)在服务端旧地面行上、客户端从未渲染，
